\section{Smart Contract Implementation}

The smart contract layer forms the core of the SkillChain platform, handling business logic, fund management, and access control. Three interconnected contracts in Solidity 0.8.24 provide complete functionality: \textit{UserProfile} for identity, \textit{JobsContract} for escrow and payment, and \textit{ProposalsContract} for the bidding workflow.

\subsection{UserProfile Contract}

The UserProfile contract manages user registration, profile data, and role assignment, serving as the platform's identity backbone since every other action is keyed on an Ethereum address. Each user is represented by a \texttt{Profile} record containing a numeric ID, a unique username, an IPFS CID pointing to off-chain metadata, a role enumeration (Client or Freelancer), and the wallet address. Two internal mappings support lookup: \texttt{\_profiles} (address → Profile) and \texttt{\_usernameOwner} (username → address) for uniqueness enforcement.

Profile creation validates the username and CID, assigns the next sequential ID, enforces uniqueness against the \texttt{\_usernameOwner} mapping (clearing the prior entry on an update), persists the record, and emits a \texttt{ProfileSet} event for off-chain indexing. Storing only minimal identity data on-chain keeps gas costs predictable; rich profile fields live on IPFS and are referenced through the single CID.

\subsection{JobsContract}

The JobsContract handles the full job lifecycle: creation with escrow, freelancer assignment, completion signalling, and payment release. It holds value at runtime and is therefore the most security-critical contract. The escrow guarantee --- funds released only when both parties signal completion --- is enforced entirely by contract logic, with no administrative override.

A \texttt{Job} record bundles a job ID, IPFS CIDs for the job description and deliverable, a completion flag, client and freelancer addresses, the escrowed amount in wei, and two independent approval booleans (one per party, since mutual approval requires remembering each signal until the other arrives). An inverse index \texttt{\_clientJobIDs} avoids scanning all jobs to render a client's dashboard.

\textbf{Job creation} validates that the message value is greater than zero, increments the job ID counter, constructs the \texttt{Job} struct with the provided CID and deposited funds, persists it, appends the ID to the client's job list, and emits a \texttt{JobCreated} event.

\textbf{Payment release} is the most security-sensitive routine because it sends ETH externally. It is invoked internally whenever a party records their completion approval and both flags are now true. The function follows the \textbf{Checks-Effects-Interactions} pattern: it checks that both parties have approved and the job is not already completed; commits the effect by marking the job complete and zeroing the stored amount \emph{before} any external call; then performs the transfer using a low-level call, with the return value checked and the transaction reverted on failure. Zeroing the balance before the transfer neutralises any re-entrancy attempt.

\subsection{ProposalsContract}

The ProposalsContract manages bidding: it accepts proposals from freelancers, exposes them for client review, and orchestrates the hiring step when a proposal is approved. It is the only contract that calls into another contract during ordinary user activity. It declares a minimal \texttt{IJobsContract} interface with two methods --- \texttt{getJobOwner} for verifying approval authority and \texttt{HireFreelancer} for assigning the freelancer --- which keeps the cross-contract dependency explicit and auditable.

A \texttt{Proposal} record contains the proposal ID, an IPFS CID with cover letter and bid details, the target job ID, an approval flag, and the submitting freelancer's address. Three mappings support lookup: \texttt{\_proposals} for direct access, \texttt{\_jobProposalIDs} for client review, and \texttt{\_freelancerProposalIDs} for freelancer dashboards.

\textbf{Proposal approval} retrieves the proposal, ensures it is not already approved, queries the JobsContract for the canonical job owner, asserts that the caller is that owner, marks the proposal approved \emph{before} the external call, invokes \texttt{HireFreelancer} on the JobsContract, and emits a \texttt{ProposalApproved} event.

\section{Frontend Implementation}

\subsection{Project Structure}

The frontend is implemented in Next.js 16 using the App Router. The codebase is organised into \texttt{app/} (routed pages), \texttt{components/} (UI primitives), \texttt{providers/} (Web3 context), \texttt{store/} (Zustand state), \texttt{lib/} (IPFS helpers), and \texttt{abi/} (JSON ABIs from the Foundry build). Components consume typed hooks wrapping wagmi calls referenced against the ABIs, isolating blockchain concerns from UI concerns and making contract upgrades a localised change.

\subsection{State Management}

Application state is divided between two complementary stores. \textbf{Wagmi and React Query} together manage all on-chain (server) state: account connection, contract reads, transaction status, and cache invalidation. \textbf{Zustand} manages cross-component UI state that does not belong on-chain --- the resolved user profile (on-chain identity combined with IPFS metadata), the connection status, and a registration flag. The store persists to \texttt{localStorage} so a returning user sees their profile rehydrate immediately on page load.

\subsection{IPFS Integration}

All variable-length content (profile metadata, job descriptions, proposal cover letters, deliverable references) is uploaded to IPFS via Pinata. The frontend exposes two thin helpers: an upload function that serialises a JavaScript object to JSON, wraps it in a \texttt{File}, posts it to Pinata's pinning endpoint with bearer authentication, and returns the resulting CID; and a fetch function that dereferences a CID through the configured Pinata gateway. Centralising IPFS access in two stateless functions makes swapping pinning providers a single-file change.

\subsection{Blockchain Configuration}

Web3 connectivity is established through a single wagmi configuration created with RainbowKit's \texttt{getDefaultConfig} helper, declaring the application name, a WalletConnect project ID, the supported chains, and an HTTP transport per chain. During development the only configured chain is the Foundry local node on port 8545; production deployments add Sepolia and mainnet entries. The rest of the application remains chain-agnostic.

\subsection{Gas Optimization and Access Control}

Gas optimization combines several techniques: \texttt{calldata} for unmodified parameters avoids memory copy costs; struct fields are ordered so smaller types share 32-byte slots; read-only functions are marked \texttt{view} and cost no gas externally; values needed only for off-chain indexing are emitted as events rather than stored; and validation checks at the start of each function revert before consuming gas on later logic.

Access control is enforced through inline checks at the start of each state-changing function: \texttt{setProfile} and \texttt{CreateJob} are open; \texttt{HireFreelancer} may only be invoked by the job's client or, transitively, by the ProposalsContract on the client's behalf; \texttt{ApproveProposal} is restricted to the job owner as verified by a live query to JobsContract; and the completion functions are restricted to the assigned freelancer and the job's client respectively. Failed checks revert with descriptive error messages.
